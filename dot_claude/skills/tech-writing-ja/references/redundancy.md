## 4. 内容のない前置きと締め

次は書かない。

| 型 | 例 | 理由 |
|----|---|------|
| 節の予告 | 「本節では〜について説明する」 | 見出しで自明 |
| 図表の予告 | 「以下に〜を示す」 | 直後にあるなら不要。番号で参照する場合のみ書く |
| 注意の前置き | 「〜であることに注意されたい」 | 注意事項は箇条書きか警告ブロックに置く |
| 章末の要約 | 「以上のように」「まとめると」 | 節が3つ以上ある章の末尾を除く |
| ブログ調 | 「本記事では」「今回は」「それでは」 | 技術文書に不要 |
| 感想 | 「〜は非常に興味深い」 | 判断に使えない |
| 断り | 「詳細は割愛するが」 | 割愛するなら書かない。必要なら参照先を書く |

## 5. 構成の冗長

| 症状 | 対処 |
|------|------|
| 「概要」「詳細」「まとめ」で同じ内容を3回書く | 1回にする。再掲は見出しへのリンクにする |
| 見出しの直後に見出しの言い換えを書く | 削る |
| 箇条書きの各項目を地の文で言い直す | どちらか一方にする |
| 根拠のない三つ組を並べる | 一つに絞るか、それぞれに根拠を付ける |
| 評価形容詞（「強力な」「便利な」「モダンな」） | 比較対象と測定値がなければ削る |
| 読み手を軽んじる語（「簡単に」「単に」「もちろん」） | 削る |
| 太字が一段落に2箇所以上 | 箇条書きか表に変える |
| 絵文字、感嘆符 | 削る |
| 読者への呼びかけ（「〜しましょう」） | 命令形にする |

## 6. 例

### 例1: 述語と重複

**前**（118字）

> 本機能を利用することにより、ユーザーは複数のファイルを一括してアップロードすることが
> 可能となっています。なお、アップロードの処理を行う際には、あらかじめ事前にファイルの
> 形式を確認しておく必要があります。

**後**（52字）

> 複数のファイルを一括アップロードできる。
> アップロード前にファイル形式を検査する。形式が不正なら 400 を返す。

削ったもの: 「〜することにより」「〜することが可能となっています」「処理を行う」
「あらかじめ事前に」「〜しておく必要があります」。
足したもの: 検査に失敗したときの挙動（W-301 の「要求」として書けていなかった）。

### 例2: 構成の冗長

**前**

> ## キャッシュ戦略について
>
> ここではキャッシュ戦略について説明します。キャッシュ戦略とは、どのようにキャッシュを
> 使うかという方針のことです。適切なキャッシュ戦略を採用することで、パフォーマンスの向上、
> コストの削減、ユーザー体験の改善といったさまざまなメリットを得ることができます。

**後**

> ## キャッシュ戦略
>
> read-through 方式を採る。TTL は 60 秒。
> 実測で API の p95 応答時間が 340 ms から 45 ms に下がった。

削ったもの: 見出しの言い換え、既知語の説明、根拠のない三つ組。
足したもの: 実際の方針と測定値（W-303）。

### 例3: 断定

**前**

> この実装ではメモリリークが発生する可能性があると考えられます。おそらく、
> リスナーの解除が行われていないことが原因ではないかと思われます。

**後**

> `subscribe` で登録したリスナーを `unsubscribe` していないため、
> 画面遷移のたびにリスナーが増える。100 回遷移した時点でヒープが 42 MB 増えることを確認した。

**未確認の場合の書き方**

> `subscribe` したリスナーを `unsubscribe` していない。メモリリークの疑いがある。
> 未確認: 画面遷移を 100 回繰り返し、`node --inspect` でヒープを比較して確かめる。
