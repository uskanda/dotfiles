# 規約ドラフト: ソースコード内コメントの規約

対象読者: このリポジトリの管理者と、規約を読む Claude Code。
前提知識: [`core-ja.md`](core-ja.md) の共通規約、担当言語の標準的な文書化形式。

skill `tech-writing-ja` の参照ファイル `references/code-comments-ja.md` に入れる想定のドラフト。
ID は `C-*` とする。

コメントは文書と条件が違う。**行数が限られ、コードと同時に腐る。**
そのため共通規約より禁止事項を強くする。

---

## 1. 言語

- **C-100**: 既存のコメントの言語に合わせる。混在している場合は日本語を使う。
- **C-101**: 公開する OSS、および英語話者が読む可能性のある repository では英語で書く。
- **C-102**: 識別子は英語のまま書く。コメント中で識別子を和訳しない。

## 2. 書く対象

- **C-200**: コメントには**なぜ**を書く。**何を**しているかはコードで表す。
- **C-201**: 次のいずれかに当たる場合はコメントを書く。当たらない場合は書かない。

  1. 非自明な理由でその実装を選んだ（性能、互換性、外部仕様、既知の不具合の回避）
  2. 外部の仕様、規格、issue、RFC への参照が必要
  3. 一見すると誤りに見えるが正しいコード
  4. 呼び出し側が守るべき契約（計算量、thread 安全性、副作用、前提条件）
  5. 単位、座標系、時刻の timezone、文字符号化など、型に現れない前提
  6. 意図的に実装していない範囲と、その理由

- **C-202**: 却下した実装案がある場合、却下の理由を1行で書く。
  同じ検討を後任に繰り返させない。

## 3. 書かない対象

- **C-300**: コードを読めば分かることを書かない。

  ```go
  // 悪い例
  // ユーザーを取得する
  user := getUser(id)
  ```

- **C-301**: 変更履歴を書かない。Git が持っている。
  `// 2025-03-01 田中 修正` のような行を残さない。
- **C-302**: コメントアウトしたコードを残さない。削除する。
- **C-303**: 飾り枠、区切り線の羅列を書かない。
- **C-304**: 関数名・変数名の言い換えを書かない。
  言い換えが要るなら、名前のほうを直す。
- **C-305**: 「〜を行う」「〜する処理」と書かない（W-200）。「〜する」と書く。
- **C-306**: 自明な引数説明を docstring に並べない。
  `id: ID` のような記述は情報量がゼロである。

## 4. 分量

- **C-400**: 関数内のコメント行は、その関数の実装行数の**2割まで**を目安とする。
  超える場合は、コードが複雑すぎるか、コメントが「何を」を説明している。
- **C-401**: 1つのコメントは3行までを目安とする。
  それ以上の説明が要るなら、設計文書に書いてコメントからリンクする。
- **C-402**: 段落コメントは、その直後のコードのまとまり全体にかかるものに限る。

## 5. タグ

- **C-500**: 使うタグを次の5つに限定する。

  | タグ | 意味 | 必須の付随情報 |
  |------|------|---------------|
  | `TODO` | 未実装。いずれやる | 追跡先（issue 番号か担当） |
  | `FIXME` | 既知の不具合。動くが正しくない | 症状と、直せていない理由 |
  | `NOTE` | 読み手が誤解しやすい点の補足 | なし |
  | `HACK` | 望ましくないが必要な回避策 | 回避している理由と、解消の条件 |
  | `SAFETY` | 安全性の前提（unsafe、並行、外部入力） | 満たすべき前提条件 |

- **C-501**: `TODO` には必ず追跡先を書く。追跡先のない `TODO` を書かない。

  ```rust
  // TODO(#412): 再試行の上限を設定から読む。現在は定数。
  ```

- **C-502**: `XXX` `???` `後で直す` を使わない。

## 6. API 文書化コメント

- **C-600**: 公開 API（外部から呼ばれる関数、型、module）には文書化コメントを書く。
  非公開の要素には、C-201 に当たる場合だけ書く。
- **C-601**: 言語標準の形式に従う。JSDoc、TSDoc、rustdoc、Python の docstring、GoDoc など。
  独自形式を作らない。
- **C-602**: 文書化コメントに書く項目。

  1. 何を返すか（1文。「〜を返す」）
  2. 引数の意味のうち、型と名前から読み取れないもの
  3. 失敗する条件と、そのときの挙動（例外、error 値、panic）
  4. 副作用（I/O、大域状態の変更、ロックの取得）
  5. 呼び出し側が守る前提条件

- **C-603**: 1文目は要約とし、そこで文を終える。
  多くの言語処理系が1文目を一覧表示に使う。
- **C-604**: 使用例は、その API の使い方が非自明なときだけ付ける。

## 7. コメントの保守

- **C-700**: コードを変更したら、その範囲のコメントを同じ commit で更新する。
- **C-701**: 内容が古いコメントを見つけたら、直すか消す。放置しない。
- **C-702**: コメントとコードが食い違う場合、コードが正である。
  ただし食い違いは不具合の兆候であり、報告する。

## 8. 例

**悪い例**

```typescript
/**
 * ユーザーを取得する関数
 * @param id ID
 * @returns ユーザー
 */
// ユーザーが存在するかチェックする
// 存在しない場合はnullを返す
async function getUser(id: string): Promise<User | null> {
  // キャッシュから取得を試みる
  const cached = cache.get(id);
  if (cached) return cached;
  // DBから取得する
  return await db.users.findOne({ id });
}
```

コメントがコードの逐語訳になっており、情報が増えていない。

**良い例**

```typescript
/**
 * ID に対応する利用者を返す。存在しなければ null を返す。
 *
 * キャッシュを参照するため、削除直後の呼び出しでは最大 60 秒間
 * 古い値を返す場合がある。強い整合性が要るなら `getUserFresh` を使う。
 */
async function getUser(id: string): Promise<User | null> {
  const cached = cache.get(id);
  if (cached) return cached;
  return await db.users.findOne({ id });
}
```

呼び出し側が知らなければ誤用する事実（キャッシュ由来の遅延と代替 API）だけを書いている。
