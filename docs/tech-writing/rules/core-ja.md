# 規約ドラフト: 日本語技術文書の共通規約

対象読者: このリポジトリの管理者と、規約を読む Claude Code。
前提知識: Markdown、技術文書の一般的な構成。

skill `tech-writing-ja` の本体に入れる想定の規約本文。議論用のドラフトである。
出典とライセンスは [`../survey.md`](../survey.md) を参照。

規約の各項目には ID を振った（`W-*` = Writing）。議論と例外申請はこの ID で行う。

---

## 0. 適用範囲と優先順位

- **W-000**: 本規約は日本語で書く技術文書すべてに適用する。README、設計書、仕様書、運用手順書、
  調査報告、Issue、PR 説明、コミットメッセージの本文を含む。
- **W-001**: プロジェクト固有の規約が存在する場合、それが本規約に優先する。
  既存文書の文体・用語は、本規約より既存文書に合わせる。
- **W-002**: 本規約に反する既存文書を、依頼されていないのに書き換えない。

## 1. 文体

- **W-100**: 一つの文書の中で文体を混ぜない。既定は**常体（である調）**とする。
  チュートリアルと手順書、および外部公開の README は敬体（ですます調）でもよい。
- **W-101**: 一文は一つのことだけを述べる。**目安60〜80字、上限90字**。
  90字を超えたら文を分ける。
- **W-102**: 読点は一文に**3つまで**。4つ必要になったら文の構造を疑う。
  ただし語の列挙（「A、B、C、D」）は数えない。列挙が4語を超えるなら箇条書きにする。
- **W-103**: 体言止めは箇条書きの項目と表のセルでのみ使う。地の文では使わない。
- **W-104**: 二重否定を使わない。「〜しないわけではない」→「〜する場合がある」。
- **W-105**: 同一の助詞を一文に連続させない（「〜の〜の〜」「〜が〜が〜」）。
- **W-106**: 同一の接続詞を連続する文の頭に置かない。
- **W-107**: 漢字の連続は6字までを目安とし、超える場合は読点か仮名で切る。
- **W-108**: 感嘆符と疑問符を本文に使わない。
- **W-109**: 一段落は3〜5文。段落の先頭に結論を置く。

## 2. 冗長の排除

**W-200**: 次の表の左を書かない。右に置き換える。

| 冗長 | 簡潔 | 備考 |
|------|------|------|
| 〜することができる | 〜できる | |
| 〜することが可能である | 〜できる | |
| 〜を行う | 〜する | 「処理を行う」など定着した複合語は例外 |
| 〜を実施する / 〜を実行する | 〜する | |
| 〜という処理を行う | 〜する | |
| 〜であると言える | 〜である | |
| 〜であると考えられる | 〜である | 断定できないなら W-300 に従う |
| 〜となっている | 〜である | |
| 〜するようにする | 〜する | |
| 〜していく / 〜していきます | 〜する | |
| 〜する必要がある | 〜する | 必要性そのものが主題の場合を除く |
| 〜に関しては / 〜については | 〜は | |
| 〜という点において | 〜で | |
| 〜の場合においては | 〜の場合は | |
| 〜することにより | 〜すると / 〜で | |
| 〜な形で / 〜という形で | （削除） | |
| 〜ということ | 〜こと / 動詞で書き直す | |
| まず初めに | まず | |
| あらかじめ事前に | 事前に | |
| 約〜程度 | 約〜 | |
| 各〜ごとに | 〜ごとに | |
| 一つ一つ個別に | 個別に | |
| 必ず〜する必要がある | 〜しなければならない | |

**W-201**: 次の前置き・締めを書かない。

- 「本節では〜について説明する」（見出しで自明）
- 「以下に〜を示す」（直後に示すなら不要。表番号で参照する場合のみ書く）
- 「〜であることに注意されたい」（注意事項は箇条書きか警告ブロックに置く）
- 「以上のように」「まとめると」で始まる要約（節が3つ以上ある章の末尾を除く）
- 「本記事では」「今回は」（ブログ調）

**W-202**: 同じ内容を「概要」「詳細」「まとめ」で繰り返さない。
文書内で同じ事実を述べてよいのは1回である。再掲が必要なら見出しへのリンクで参照する。

**W-203**: 見出しの直後に、見出しを言い換えただけの文を置かない。

**W-204**: 箇条書きの各項目を、直後の地の文で言い直さない。

**W-205**: 内容の増えない列挙をしない。
「保守性、可読性、拡張性が向上する」のように根拠のない三つ組を並べない。
一つに絞るか、それぞれに根拠を付ける。

**W-206**: 評価形容詞は根拠とセットでのみ使う。
「強力な」「便利な」「素晴らしい」「モダンな」は、比較対象と測定値がなければ削る。

**W-207**: 読み手を軽んじる語を使わない。「簡単に」「単に」「もちろん」「言うまでもなく」。
読み手にとって簡単とは限らない。

**W-208**: 太字は一段落に1箇所まで。強調が3箇所以上必要なら、箇条書きか表に変える。

**W-209**: 絵文字を使わない。

**W-210**: 読者への呼びかけ（「〜しましょう」「〜してみましょう」）を書かない。
手順書の命令形（「〜する」「〜を実行する」）に置き換える。

**W-211**: 書き終えたら、**意味を変えずに20%短くできないか試す**。
できるなら短くする。この工程は省略しない（§7 参照）。

## 3. 断定と根拠

- **W-300**: 「〜と思われる」「〜かもしれない」「〜と考えられる」「〜のような気がする」を書かない。
- **W-301**: 事実・要求・推測を書き分ける。
  - 事実 → 断定する。「〜である」
  - 要求・仕様 → §5 の要求レベル語を使う
  - 未確認 → 「未確認」と明記し、確認方法（コマンド、参照先、担当）を書く
- **W-302**: 検証していないことを検証したように書かない。
  実行したコマンドと結果を書ける場合は書く。
- **W-303**: 数値・制限・既定値には出典を付ける。出典を示せない数値は書かない。

## 4. 用語

**この節が本規約の中心である。**

- **W-400**: 文書の冒頭に**対象読者**と**前提知識**を書く。1〜3行でよい。

  ```markdown
  対象読者: 本リポジトリのバックエンド開発者。
  前提知識: Go の基本文法、gRPC の概念。
  ```

- **W-401**: **W-400 で宣言した前提知識に含まれない用語は、初出時に必ず処理する。**
  処理は次の三つのいずれかとする。

  | 対応 | 判断基準 | 書き方 |
  |------|---------|--------|
  | (a) 言い換える | 一般語で意味が保てる | 専門用語を使わない |
  | (b) 説明を付けて使う | 用語自体が必要 | `用語（＝1行の定義）` または直後の1文で定義する |
  | (c) そのまま使う | 前提知識に含まれる | そのまま書く |

  迷ったら (b) を選ぶ。

- **W-402**: 略語は初出で「正式名称（略語）」と書き、以降は略語を使う。
  1文書あたりの略語は10個までを目安とする。
- **W-403**: 定義が必要な用語が**5個以上**になったら、独立した用語集の節またはファイルを作る。
- **W-404**: 1つの概念に1つの語を割り当てる。表記ゆれを混ぜない。
  例: 「ユーザー / ユーザ / 利用者」、「取得する / 取ってくる / フェッチする」。
- **W-405**: チーム内の隠語・社内固有の呼称を、定義なしに使わない。
- **W-406**: 外来語は、定訳がある場合は日本語を使う。
  - 日本語を使う: 可用性（availability）、冪等（idempotent）、直列化（serialization）
  - 原語のまま使う: デプロイ、コミット、マージ、キャッシュ（技術分野で定着している）
  - 判断基準は「その分野の日本語技術書で一般的か」とする。判断できない場合は
    初出で「カタカナ（英字）」と併記する。
- **W-407**: 半角カナを使わない。
- **W-408**: 英数字は半角、和文の記号は全角とする。

## 5. 要求レベル（RFC 2119 対応）

**W-500**: 仕様・要求を書くときは次の対応表に従う。曖昧語（「なるべく」「原則として」）を使わない。

| RFC 2119 | 日本語 | 意味 |
|----------|--------|------|
| MUST / SHALL / REQUIRED | 〜しなければならない | 絶対要求 |
| MUST NOT / SHALL NOT | 〜してはならない | 絶対禁止 |
| SHOULD / RECOMMENDED | 〜すべきである | 例外を認めるが理由の記述が要る |
| SHOULD NOT | 〜すべきでない | 同上 |
| MAY / OPTIONAL | 〜してもよい | 任意 |

**W-501**: SHOULD / SHOULD NOT を使う場合、例外が認められる条件を同じ節に書く。

## 6. 構造

- **W-600**: 文書を書き始める前に種類を一つ決め、混ぜない。

  | 種類 | 目的 | 読み手の状態 |
  |------|------|-------------|
  | チュートリアル | 学ぶ | 何も知らない。手を動かして体験する |
  | 手順書（ハウツー） | 作業する | 目的を持っている。手順だけ要る |
  | リファレンス | 調べる | 作業中。事実を正確に引きたい |
  | 説明 | 理解する | 背景・設計判断・理由を知りたい |

  一つの文書で二つ以上を扱わない。必要なら文書を分けてリンクする。

- **W-601**: 結論を先に書く。背景 → 結論の順にしない。
- **W-602**: 見出しは名詞句または動詞句にする。文にしない。同じ階層で粒度を揃える。
- **W-603**: 箇条書きは3項目以上のときだけ使う。2項目なら文で書く。
- **W-604**: 箇条書きの項目は文法形式を揃える。全部を名詞句にするか、全部を動詞句にする。
- **W-605**: 箇条書きのネストは2階層まで。
- **W-606**: 手順は番号付きリスト、選択肢と列挙は記号リストを使う。
- **W-607**: 表は2軸以上の比較にだけ使う。1軸なら箇条書きで書く。
- **W-608**: コードブロックには言語を明示する。省略部分は `# ...` のようにコメントで示す。
- **W-609**: 図は Mermaid を既定とする。文章で足りることを図にしない。
- **W-610**: リンクテキストはリンク先の内容を表す語にする。「こちら」「リンク」を使わない。
- **W-611**: 位置で参照しない。「上記」「下記」「先ほどの」を使わず、見出し名か節番号で参照する。
- **W-612**: 時間に依存する記述をしない。
  「現在」「最新」「新しい」を避け、版番号か日付で書く。
  最終更新日はファイル冒頭ではなく Git の履歴に任せる。

## 7. 書き終えた後の自己校閲

**W-700**: 文書を出力する前に、次を順に実行する。省略しない。

```
- [ ] 1. §2 の置換表に載る表現が残っていないか検索する
- [ ] 2. 90字を超える文がないか確認する
- [ ] 3. 前提知識（W-400）に無い用語が、定義なしで使われていないか確認する
- [ ] 4. 同じ事実を2回以上書いていないか確認する
- [ ] 5. 意味を変えずに20%短くする（W-211）
- [ ] 6. textlint があれば実行する
```

**W-701**: 5 で短くできなかった場合は、その理由を1行で報告する。

**W-702**: 規約に反することを意図的に行った場合、該当する規約 ID と理由を報告に書く。
黙って逸脱しない。

## 8. 機械検査（任意）

**W-800**: textlint を導入している場合、次を最低限の構成とする。

```json
{
  "rules": {
    "preset-ja-technical-writing": {
      "sentence-length": { "max": 90 },
      "no-exclamation-question-mark": true,
      "ja-no-weak-phrase": true,
      "ja-no-redundant-expression": true
    }
  }
}
```

**W-801**: 表記ゆれ（W-404）はプロジェクトごとの `prh` 辞書で管理する。
辞書がないうちは W-404 を人と Claude の判断で運用する。
