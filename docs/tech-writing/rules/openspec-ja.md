# 規約ドラフト: OpenSpec 成果物の日本語規約

対象読者: このリポジトリの管理者と、規約を読む Claude Code。
前提知識: [`core-ja.md`](core-ja.md) の共通規約、OpenSpec の CLI と成果物の構成。

skill `tech-writing-ja` の参照ファイル `references/openspec.md` に入れる想定のドラフト。共通規約（`W-*`）に加えて適用する。
ID は `OS-*` とする。

出典: [OpenSpec](https://github.com/Fission-AI/OpenSpec)（MIT）の
`openspec/specs/openspec-conventions/spec.md` および `docs/concepts.md`。

---

## 1. 日本語化してよい範囲

**OS-100**: OpenSpec の CLI は見出し文字列とキーワードを解析対象にする。
次の要素は**英語のまま**にしなければならない。翻訳すると `openspec validate` と
アーカイブ時の差分適用が壊れる。

| 要素 | 形式 | 日本語化 |
|------|------|---------|
| 要求の見出し接頭辞 | `### Requirement: ` | 不可 |
| シナリオの見出し接頭辞 | `#### Scenario: ` | 不可 |
| シナリオのキーワード | `**GIVEN**` `**WHEN**` `**THEN**` `**AND**` | 不可 |
| 差分の節見出し | `## ADDED Requirements` ほか | 不可 |
| 差分の節見出し（残り） | `## MODIFIED / REMOVED / RENAMED Requirements` | 不可 |
| 能力の目的 | `## Purpose` | 不可 |

**OS-101**: 次の要素は日本語で書く。

- 要求名（`### Requirement:` の後ろ）
- 要求の本文
- シナリオ名（`#### Scenario:` の後ろ）
- シナリオの各行の内容
- `proposal.md` / `design.md` / `tasks.md` の本文

**OS-102**: 見出しレベルを守る。要求は `###`、シナリオは `####`。
`###` のシナリオや箇条書きによるシナリオは、警告なしに無視される。

## 2. 要求（Requirement）

**OS-200**: 要求名は日本語の名詞句とし、**50字未満**にする。
1つの spec 内で重複してはならない。要求名は差分適用の一意識別子である。

```markdown
### Requirement: テーマの切り替え
```

**OS-201**: 要求名を後から変えるときは、本文を書き換えずに
`## RENAMED Requirements` で旧名と新名を明示する。

**OS-202**: 要求の1文目に、要求レベル語を含む断定文を書く。
共通規約 W-500 の対応表に従う。

**OS-203**: `openspec validate` は要求本文に英語の `SHALL` / `MUST` を探す。
日本語だけで書くと検出されないため、**英語キーワードを括弧で併記する**。

```markdown
### Requirement: テーマの切り替え

システムは、利用者がライトテーマとダークテーマを切り替えられるようにしなければならない（SHALL）。
既定値は OS の設定に従う。
```

> 未検証: 使用中の openspec の版で、この併記形式が validate を通るかは確認していない。
> 導入時に `openspec validate` を1回実行して確かめること。
> 通らない場合は要求の1文目のみ英語で書き、2文目以降を日本語にする。

**OS-204**: 要求には**外部から観測できる振る舞い**だけを書く。
インタフェース、入出力、エラー時の挙動、制約が対象である。
ライブラリの選定、クラス構成、実行の仕組みは `design.md` か `tasks.md` に書く。

**OS-205**: 1つの要求には少なくとも1つのシナリオを付ける。

**OS-206**: 要求の粒度は、変更の risk に比例させる。
局所的で低リスクな変更は、簡潔な振る舞い記述だけでよい。
チームや repository をまたぐ変更、API の互換性を壊す変更、移行を伴う変更、
セキュリティとプライバシーに関わる変更では、検証条件まで明示する。

## 3. シナリオ（Scenario）

**OS-300**: シナリオは検証可能な事象を1つだけ書く。
「〜が正しく動作する」のような検証不能な記述をしない。

**OS-301**: キーワードは英語の太字、内容は日本語で書く。

```markdown
#### Scenario: テーマ切り替えボタンを押す

- **GIVEN** 利用者がライトテーマで画面を開いている
- **WHEN** テーマ切り替えボタンを押す
- **THEN** 画面がダークテーマに切り替わる
- **AND** 選択したテーマが次回起動時まで保持される
```

**OS-302**: シナリオ名は「操作」または「状況」を表す日本語にする。
`Scenario: 正常系` のような分類名を使わない。

**OS-303**: 補足はキーワード行の下に字下げした箇条書きで書く。
`####` より深い見出しを作らない。

## 4. 差分（delta spec）

**OS-400**: 差分には変更点だけを書く。変更後の spec 全体を書かない。

**OS-401**: 節ごとの規則。

| 節 | 内容 |
|----|------|
| `## ADDED Requirements` | 新しい要求。要求名とシナリオまで全文書く |
| `## MODIFIED Requirements` | 変更後の要求を**全文**書く。差分だけを書かない。見出しは既存の spec と同一にする |
| `## REMOVED Requirements` | 見出しのみ。削除の理由と移行手段を書く |
| `## RENAMED Requirements` | 旧名と新名 |

**OS-402**: `## Purpose` を書くのは、その能力（capability）の spec を新規に作るときだけとする。
既存の能力に対する差分には書かない。既存の Purpose が正である。

**OS-403**: `MODIFIED` では、変更箇所に `← （変更前: 30秒）` のような注記を付けてよい。

## 5. proposal.md

**OS-500**: 構成は次の4つとする。各節は簡潔に書く。

```markdown
## なぜ
（1〜3文。解決したい問題と、放置した場合の影響）

## 対象範囲
含む:
- ...
含まない:
- ...

## 方針
（1段落。とる手段の概要）

## 影響
（変更が及ぶ範囲。利用者から見える変化があれば明記する）
```

**OS-501**: 「含む」と「含まない」を対で書く。「含まない」を空にしない。
何をやらないかを書かない提案は、範囲が曖昧である。

**OS-502**: 変更の記述には From / To / 理由 / 影響 を含める。

## 6. design.md

**OS-600**: 設計判断は次の形式で書く。1判断につき1ブロックとする。

```markdown
### 判断: セッション保存先に SQLite を使う

- 文脈: 単一利用者の CLI であり、常駐 process を置きたくない
- 選択肢: SQLite / PostgreSQL / JSON ファイル
- 決定: SQLite
- 理由: 埋め込みで動き、offline で使え、単一ファイルで持ち運べる
- 影響: 同時書き込みは想定しない。将来 sync が必要になれば再検討する
```

**OS-601**: 採用しなかった選択肢と、却下の理由を書く。
却下理由のない設計文書は、後から読む人に同じ検討をやり直させる。

**OS-602**: 図が判断の理解を助ける場合だけ図を描く（W-609）。

## 7. tasks.md

**OS-700**: 1タスクは**1セッションで完了する粒度**にする。

**OS-701**: タスクは動詞で始める。「〜の対応」「〜まわり」のような名詞止めを使わない。

**OS-702**: 各タスクに完了条件を書く。テストが通ること、コマンドが成功することなど、
判定できる形で書く。

```markdown
## 1. データ層

- [ ] 1.1 `themes` テーブルの migration を追加する（`make migrate` が成功すること）
- [ ] 1.2 テーマの読み書き関数を実装する（単体テストが通ること）
```

**OS-703**: 関連するタスクを見出しでまとめ、`1.1` `1.2` の階層番号を振る。

## 8. 既存の openspec-* skill との関係

**OS-800**: このリポジトリの `dot_claude/skills/openspec-*` は openspec CLI が生成した英語の
手順書であり、**書き換えない**。CLI の更新で再生成されるため、変更は失われる。

**OS-801**: 日本語の書き方は `tech-writing-ja` skill 側に置き、
openspec-* skill が成果物を生成する場面で重ねて適用する。
