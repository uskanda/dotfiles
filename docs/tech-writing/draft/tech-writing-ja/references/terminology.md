## 1. なぜ前提知識を宣言するか

「難しい用語を避ける」という指示は守れない。**誰にとって難しいかが決まっていない**からである。
前提知識を文書に書けば、既知か未知かを機械的に判定できる。

```
宣言した前提知識に含まれる  → そのまま使う
含まれない                 → 言い換えるか、定義を付ける
```

判定に迷う語がある場合、それは前提知識の宣言が粗いことを意味する。宣言のほうを直す。

## 2. 前提知識の書き方

**W-400**: 500字を超える文書は、冒頭に対象読者と前提知識を1〜3行で書く。

```markdown
対象読者: 本リポジトリのバックエンド開発者。
前提知識: Go の基本文法、gRPC の概念、本サービスのドメインモデル。
```

書き方の要点。

- 役割ではなく**知識**を書く。「エンジニア向け」では判定に使えない
- 3〜5項目に収める。多すぎる宣言は「全部既知」と同じで判定に使えない
- 対象読者が複数いる場合は、**最も知識が少ない読者**に合わせる
- 文書の種類ごとの目安

  | 種類 | 前提知識の粒度 |
  |------|--------------|
  | チュートリアル | 最小限にする。前提が多いチュートリアルは役に立たない |
  | 手順書 | 作業に必要な道具と権限まで書く |
  | リファレンス | 分野の基本知識まで。個別の実装は前提にしない |
  | 設計書・仕様書 | 対象システムのドメイン知識まで書いてよい |

## 3. 初出時の三分岐

**W-401**: 宣言に含まれない用語は、初出時に必ずどれかを選ぶ。迷ったら (b)。

### (a) 言い換える

一般語で意味が保てるなら、専門用語を使わない。

| 使わない | 使う |
|---------|------|
| 冪等性を担保する | 何回実行しても結果が変わらない |
| 疎結合化する | 依存を減らす |
| 責務を分離する | 役割ごとに分ける |
| 頻回に | 何回も |
| 惹起する | 引き起こす |

ただし**正確さを失うなら言い換えない**。「冪等」は数学的に定義された語であり、
仕様書では (b) を選ぶ。

### (b) 説明を付けて使う

用語自体が必要なときに使う。書き方は2つ。

```markdown
JWT（JSON Web Token、署名付きの認証情報）で認証する。
```

```markdown
本システムは冪等性を保証する。冪等とは、同じ要求を何回送っても
結果が1回送ったときと同じになる性質を指す。
```

定義は**1行**に収める。1行に収まらない場合、その語は文書の主題である。
独立した節を立てる。

### (c) そのまま使う

前提知識の宣言に含まれる語だけに使う。
宣言に無い語をここに分類したくなったら、宣言を直すか (b) にする。

## 4. 略語

**W-402**: 初出で「正式名称（略語）」と書き、以降は略語を使う。

```markdown
CI（Continuous Integration）を GitHub Actions で動かす。CI は push のたびに走る。
```

- 1文書あたり10個までを目安とする。超えるなら用語集を作る（W-403）
- 見出しでは略語を使わない。検索で見つからなくなる
- 分野内で完全に定着した略語（API、URL、HTTP、JSON）は展開しなくてよい
- 社内の略語は必ず展開する。定着の度合いを読み手と共有できない

## 5. 外来語とカタカナ

**W-406**: 定訳がある場合は日本語を使う。判断基準は「その分野の日本語技術書で一般的か」。

| 日本語を使う | カタカナ／原語を使う |
|------------|-------------------|
| 可用性（availability） | デプロイ |
| 冪等（idempotent） | コミット、マージ |
| 直列化（serialization） | キャッシュ |
| 一貫性（consistency） | リクエスト、レスポンス |
| 排他制御 | タイムアウト |
| 再入可能（reentrant） | トランザクション |

判断できない場合は、初出で「カタカナ（英字）」と併記する。

```markdown
アイドリング（idling）中は接続を保持しない。
```

**W-407**: 半角カナを使わない。
**W-408**: 英数字は半角、和文の記号は全角にする。

カタカナ語の長音記号は、末尾に付ける表記を既定とする（「サーバー」「ユーザー」「コンピューター」）。
プロジェクトの既存表記があればそれに従う（W-001）。

## 6. 表記ゆれ

**W-404**: 1つの概念に1つの語を割り当てる。

よく揺れる組み合わせ。

| 概念 | 揺れ | 決め方 |
|------|------|--------|
| 利用する人 | ユーザー / ユーザ / 利用者 / エンドユーザー | 1つ選ぶ。UI 文言と揃える |
| 取得 | 取得する / 取ってくる / フェッチする / 引く | 「取得する」を既定とする |
| 設定 | 設定 / コンフィグ / 構成 | 「設定」を既定とする |
| 経路 | パス / 経路 / ルート | 文脈で区別する。URL は「パス」 |
| 実行環境 | 環境 / 環境面 / インフラ | 「環境」を既定とする |
| 不具合 | バグ / 不具合 / 障害 | 「不具合」と「障害」は影響範囲で区別する |

**W-405**: チーム内の隠語を定義なしに使わない。
「例のやつ」「旧基盤」「新 API」のような呼称は、文書では正式名称に置き換える。

## 7. 用語集の作り方

**W-403**: 定義が必要な用語が5個以上になったら、独立した用語集を作る。

置き場所。

| 範囲 | 置き場所 |
|------|---------|
| 1文書内 | 文書末尾の「用語」節 |
| repository 全体 | `docs/glossary.md` |
| OpenSpec 運用中 | `openspec/project.md` の用語節 |

書き方。

```markdown
## 用語

| 用語 | 定義 |
|------|------|
| テナント | 課金と権限の単位。1テナントに複数の利用者が属する |
| 論理削除 | `deleted_at` に時刻を入れ、行を残したまま参照から外すこと |
```

- 定義は1行。50字以内を目安とする
- 定義に別の未定義語を使わない。使うなら、その語も用語集に入れる
- 五十音順かアルファベット順に並べる。分類で並べない
- 用語集にある語は、本文で再定義しない。用語集へリンクする

## 8. 判定手順

文書を出す前に実行する（W-700 の手順3）。

```
1. 文書中の専門用語・略語・社内語を洗い出す
2. 各語について:
   前提知識の宣言に含まれるか?
     はい  → そのまま（(c)）
     いいえ → 初出箇所で定義されているか?
                はい  → よし
                いいえ → (a) 言い換える か (b) 定義を付ける
3. 定義した語が5個以上なら、用語集に切り出す
4. 同じ概念に2つ以上の語を使っていないか確認する（W-404）
```
