# 日本語技術文書の規約

目的は、人が校閲する量を減らすことである。
規約の各項目には ID を振ってある（`W-*`）。逸脱するときは ID と理由を報告する。

## 手順

```
- [ ] 1. 文書の種類と読み手を決める（§1）
- [ ] 2. 前提知識を宣言する（§2）
- [ ] 3. 書く（§3〜§5）
- [ ] 4. 自己校閲する（§6）。省略しない
```

## 1. 書き始める前に決める

**W-600**: 種類を一つ決め、混ぜない。二つ扱いたくなったら文書を分ける。

| 種類 | 目的 | 読み手の状態 | 文体 |
|------|------|-------------|------|
| チュートリアル | 学ぶ | 何も知らない。手を動かす | 敬体可 |
| 手順書 | 作業する | 目的がある。手順だけ要る | 敬体可 |
| リファレンス | 調べる | 作業中。事実を引きたい | 常体 |
| 説明・設計書・仕様書 | 理解する | 背景と判断理由を知りたい | 常体 |

**W-100**: 文体は文書内で統一する。既定は常体（である調）。
既存文書がある場合は、規約より既存文書に合わせる（W-001）。

## 2. 前提知識の宣言（用語問題への対処の起点）

**W-400**: 500字を超える文書は、冒頭に対象読者と前提知識を1〜3行で書く。

```markdown
対象読者: 本リポジトリのバックエンド開発者。
前提知識: Go の基本文法、gRPC の概念。
```

**W-401**: **宣言に含まれない用語は、初出時に必ず処理する。** 迷ったら (b) を選ぶ。

| 対応 | 判断基準 | 書き方 |
|------|---------|--------|
| (a) 言い換える | 一般語で意味が保てる | 専門用語を使わない |
| (b) 説明を付けて使う | 用語自体が必要 | `用語（＝1行の定義）` か直後の1文で定義 |
| (c) そのまま使う | 前提知識に含まれる | そのまま書く |

**W-402**: 略語は初出で「正式名称（略語）」。以降は略語。1文書10個まで。
**W-403**: 定義が要る用語が5個以上になったら、用語集の節を作る。
**W-404**: 1つの概念に1つの語。表記ゆれを混ぜない（ユーザー / ユーザ / 利用者）。
**W-405**: チーム内の隠語を定義なしに使わない。

外来語の判断、用語集の作り方は `references/terminology.md` を読む。

## 3. 書かないもの

**W-200**: 次を書かない。左を書きかけたら右にする。

| 冗長 | 簡潔 |
|------|------|
| 〜することができる／〜することが可能である | 〜できる |
| 〜を行う／〜を実施する／〜を実行する | 〜する |
| 〜であると言える／〜であると考えられる | 〜である |
| 〜となっている | 〜である |
| 〜するようにする／〜していく | 〜する |
| 〜する必要がある | 〜する（必要性が主題の場合を除く） |
| 〜に関しては／〜については | 〜は |
| 〜な形で／〜という形で／〜ということ | 削る |
| まず初めに／あらかじめ事前に／約〜程度 | まず／事前に／約〜 |

全文は `references/redundancy.md` にある。

**W-201**: 内容のない前置きと締めを書かない。

- 「本節では〜について説明する」（見出しで自明）
- 「以下に〜を示す」（直後に示すなら不要）
- 「以上のように」「まとめると」で始まる要約（節が3つ以上ある章の末尾を除く）
- 「本記事では」「今回は」

**W-202**: 同じ事実を文書内で2回書かない。再掲が要るなら見出しへのリンクで参照する。
**W-203**: 見出しの直後に、見出しを言い換えただけの文を置かない。
**W-204**: 箇条書きの項目を、直後の地の文で言い直さない。
**W-205**: 根拠のない三つ組を書かない。「保守性、可読性、拡張性が向上する」は、
一つに絞るか、それぞれに根拠を付ける。
**W-206**: 評価形容詞（「強力な」「便利な」「モダンな」）は、比較対象と測定値がなければ削る。
**W-207**: 「簡単に」「単に」「もちろん」「言うまでもなく」を書かない。
**W-208**: 太字は一段落に1箇所まで。
**W-209**: 絵文字を使わない。感嘆符と疑問符を本文に使わない。
**W-210**: 「〜しましょう」「〜してみましょう」を書かない。手順は命令形で書く。

## 4. 断定と根拠

**W-300**: 「〜と思われる」「〜かもしれない」「〜と考えられる」を書かない。
**W-301**: 事実・要求・推測を書き分ける。

- 事実 → 断定する
- 要求・仕様 → §5 の要求レベル語を使う
- 未確認 → 「未確認」と明記し、確認方法（コマンド、参照先、担当）を書く

**W-302**: 検証していないことを検証したように書かない。
**W-303**: 数値・制限・既定値には出典を付ける。示せない数値は書かない。

## 5. 要求レベル（RFC 2119）

**W-500**: 曖昧語（「なるべく」「原則として」）を使わず、次に従う。

| RFC 2119 | 日本語 |
|----------|--------|
| MUST / SHALL | 〜しなければならない |
| MUST NOT / SHALL NOT | 〜してはならない |
| SHOULD | 〜すべきである |
| SHOULD NOT | 〜すべきでない |
| MAY | 〜してもよい |

**W-501**: SHOULD を使う場合、例外が認められる条件を同じ節に書く。

## 6. 文章と構造

**W-101**: 一文は目安60〜80字、上限90字。一文一義。
**W-102**: 読点は一文に3つまで（語の列挙は数えない）。
**W-103**: 体言止めは箇条書きと表のセルのみ。
**W-104**: 二重否定を使わない。
**W-105**: 同一の助詞を一文に連続させない。
**W-107**: 漢字の連続は6字まで。
**W-109**: 一段落は3〜5文。段落の先頭に結論を置く。

**W-601**: 結論を先に書く。
**W-602**: 見出しは名詞句か動詞句。文にしない。同じ階層で粒度を揃える。
**W-603**: 箇条書きは3項目以上のときだけ使う。2項目なら文で書く。
**W-604**: 箇条書きの項目は文法形式を揃える。
**W-605**: ネストは2階層まで。
**W-606**: 手順は番号付き、列挙は記号。
**W-607**: 表は2軸以上の比較にだけ使う。
**W-608**: コードブロックに言語を明示する。
**W-609**: 図は Mermaid。文章で足りることを図にしない。
**W-610**: リンクテキストは内容を表す語にする。「こちら」を使わない。
**W-611**: 「上記」「下記」ではなく見出し名で参照する。
**W-612**: 「現在」「最新」「新しい」ではなく版と日付で書く。

## 7. 出力する前の自己校閲

**W-700**: 省略しない。

```
- [ ] 1. §3 の表の表現が残っていないか検索する
- [ ] 2. 90字を超える文がないか確認する
- [ ] 3. 前提知識（W-400）に無い用語が、定義なしで使われていないか確認する
- [ ] 4. 同じ事実を2回以上書いていないか確認する
- [ ] 5. 意味を変えずに20%短くする
- [ ] 6. textlint があれば実行する
```

機械で 1、2 を確認する場合:

```bash
grep -nE 'することができ|することが可能|を行う|となっている|と思われ|と考えられ|まず初めに|な形で|という形で|する必要があ|していく|ようにする|簡単に|単に|もちろん' <file>
```

**W-701**: 5 で短くできなかった場合は、理由を1行報告する。
**W-702**: 規約に反することを意図的に行った場合、規約 ID と理由を報告に書く。黙って逸脱しない。

## 8. 用途別の追加規約

| 場面 | 読むファイル |
|------|------------|
| 冗長表現の全文が要る | `references/redundancy.md` |

| OpenSpec の proposal / design / specs / tasks を書く | `references/openspec.md` |
| ソースコメントと docstring を書く | `references/code-comments.md` |
